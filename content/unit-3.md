## 문제 추상화

컴퓨터로 문제를 해결하려면 **어떤 상태에서 시작해 어디까지 바꿀지**, 그리고 그 과정에 **어떤 정보가 필요한지**부터 정해야 해요.

![책을 자동으로 분류하는 프로그램을 사용하는 모습](assets/library-books.webp "교과서 84쪽")

### 상태 정의와 핵심 요소

- **초기 상태**는 문제 해결을 시작할 때의 상태예요. 업다운 게임을 시작하면 컴퓨터가 정답을 정하고 시도 횟수는 0이에요.
- **현재 상태**는 지금 시점의 상태예요. 예를 들어 43을 입력했고, 시도 횟수는 1번이며, 화면에는 “UP”이 나와 있어요.
- **목표 상태**는 해결을 마친 상태예요. 입력값이 정답과 같아져 ‘정답’과 시도 횟수가 표시되면 게임이 끝나요.
- **핵심 요소**는 문제 해결에 필요한 정보예요. 업다운 게임의 비교 규칙을 만들 때는 정답, 입력값, 시도 횟수가 필요해요.

![집에서 마트까지 가는 초기·현재·목표 상태](assets/problem-states.webp "교과서 85쪽")
![여행 가방에 넣을 물건을 고르며 찾아낸 핵심 요소](assets/packing.webp "교과서 86쪽")

### 구조화와 입력·처리·출력

**구조화**는 필요한 요소를 표나 그림 등으로 정리해 관계를 파악할 수 있게 하는 일이에요. **추상화**는 목표에 필요한 정보와 규칙을 골라 다루기 쉬운 형태로 표현하는 과정이에요. 업다운 게임에서 배경색은 화면을 꾸밀 때 필요하지만, 숫자를 비교하는 규칙에서는 생략할 수 있어요.

- **입력** — 학생이 추측한 숫자
- **처리** — 시도 횟수를 1 늘린 뒤, 입력한 숫자를 정답과 비교하기
- **출력** — 작으면 UP, 크면 DOWN, 같으면 정답과 시도 횟수 표시

> 숫자 비교 프로그램과 화면 꾸미기 프로그램에 필요한 정보는 다를 수 있어요. 먼저 해결하려는 문제를 정하면 필요한 요소를 판단하기 쉬워요.

## 알고리즘 표현과 분석

**알고리즘**은 문제를 해결하기 위해 순서대로 정리한 절차예요. 문제가 같아도 절차를 여러 방법으로 설계할 수 있어요.

### 알고리즘의 다섯 가지 조건

- **입력** — 문제 해결에 필요한 값을 받기. 별도의 입력이 없는 알고리즘도 있어요.
- **출력** — 문제를 해결한 결과가 나오기.
- **명확성** — 누가 읽어도 각 단계에서 할 일이 분명하기.
- **수행 가능성** — 각 단계의 명령을 실제로 실행할 수 있기.
- **유한성** — 정해진 절차를 거쳐 유한한 단계 안에 끝나기.

![음식을 주문하는 과정으로 살펴보는 알고리즘의 조건](assets/food-order.webp "교과서 91쪽")

### 자연어·의사 코드·순서도

- **자연어**는 우리가 쓰는 말로 설명해요. “입력한 수가 정답보다 작으면 UP을 보여 준다.”
- **의사 코드**는 프로그램처럼 짧고 일정한 형식으로 써요. `만약 입력값 < 정답이면 → UP 출력`
- **순서도**는 약속된 도형과 흐름선으로 실행 순서를 그려요. 둥근 **단말**은 시작·끝, **평행사변형**은 입력·출력, **직사각형**은 처리, **마름모**는 판단이에요. 판단에서는 보통 ‘예’와 ‘아니요’로 흐름이 나뉘어요.

![순서도 기호와 두 수를 더하는 순서도 예시](assets/flowchart.webp "교과서 93쪽")
![반복과 공식을 이용해 1부터 n까지의 합을 구하는 두 가지 순서도](assets/algorithm-comparison.webp "교과서 95쪽")

### 제어 구조와 비교 기준

- **순차 구조** — 정해진 순서대로 실행해요.
- **선택 구조** — 조건의 참·거짓에 따라 실행할 절차를 정해요.
- **반복 구조** — 동작을 정해진 횟수만큼 또는 조건에 따라 여러 번 실행해요.

알고리즘을 비교할 때는 **정확한 결과**, **이해와 수정의 편의**, **작업량·수행 시간**, **기억 공간 사용량**을 살펴봐요. 예를 들어 1부터 100까지 계속 더할 수도 있고, `100 × 101 ÷ 2`로 구할 수도 있어요. 이 문제에서 공식을 써서 계산하면 매번 더하는 작업이 줄어들어요.

### 문제 해결 전략

- **전체 탐색** — 후보를 차례로 조사해요. 정리되지 않은 리스트에서 친구 이름을 앞에서부터 찾는 경우예요.
- **분할 정복** — 큰 문제를 작은 문제들로 나누어 해결한 뒤 결과를 합쳐요. 여러 묶음을 각각 정렬한 다음 순서에 맞게 합치는 경우예요.
- **규칙 찾기** — 반복되는 패턴을 이용해요. 빨강·파랑이 번갈아 나올 때 다음 색을 예측하는 경우예요.
- **되추적** — 선택한 길에서 해결할 수 없으면 이전 선택 지점으로 돌아가 다른 방법을 시도해요. 미로 탐색이 한 예예요.

![번호대별로 시험지를 나누어 정리하는 장면](assets/divide-conquer.webp "교과서 97쪽")
![체스에서 잘못된 선택을 되돌려 다른 수를 생각하는 장면](assets/backtracking.webp "교과서 98쪽")

## 데이터 순차 저장 및 활용

**변수**는 값을 담는 이름 있는 저장 공간, **리스트**는 여러 값을 순서대로 담는 저장 공간이에요. 예를 들어 현재 점수는 변수 하나에, 친구들이 입력한 역대 점수는 리스트에 담을 수 있어요.

- 리스트 안에 들어 있는 값 하나하나를 **항목**이라고 해요.
- **엔트리와 스크래치**에서는 첫 번째 항목의 번호가 1이에요.
- 끝에 **추가**하거나 중간에 **삽입**할 수 있고, 번호를 이용해 **읽기·수정·삭제**할 수 있어요.
- 중간에 항목을 삽입하거나 삭제하면 뒤쪽 항목의 번호가 바뀌어요.

![한 장소에 여러 항목을 순서대로 저장하는 리스트의 개념](assets/list-storage.webp "교과서 107쪽")
![엔트리와 스크래치의 리스트 명령 블록](assets/list-blocks.webp "교과서 109쪽")

> 메뉴 리스트가 [김밥, 떡볶이, 어묵]일 때 2번 항목을 삭제하면, 원래 3번이었던 어묵이 2번이 돼요.

## 논리 연산과 중첩 제어 구조

**논리 연산**을 하면 결과가 참 또는 거짓으로 나와요. 조건문이나 반복문의 조건을 만들 때 사용해요.

- **AND(그리고)** — A와 B가 모두 참일 때만 참이에요. ‘생명이 남아 있고 AND 딸기에 닿았으면’ 보너스 점수를 줘요.
- **OR(또는)** — A와 B 중 하나 이상 참이면 참이에요. **두 조건이 모두 참이어도** 참이에요.
- **NOT(아니다)** — 조건 하나의 참과 거짓을 뒤집어요. ‘벽에 닿지 않았으면 이동’처럼 표현해요.

![AND, OR, NOT의 참·거짓을 비교하는 표](assets/logic-table.webp "교과서 118쪽")

### 제어문 안의 제어문

**중첩 제어**는 반복문이나 조건문 안에 또 다른 제어문을 넣는 방식이에요. 바깥 구조가 먼저 실행되고, 안쪽 구조는 바깥 구조의 흐름에 따릅니다.

- **반복문 안의 조건문** — 업다운 게임에서 정답을 맞힐 때까지 입력을 받고, 매번 입력값이 더 작은지 판단해요.
- **반복문 안의 반복문** — 3줄에 매번 별 4개를 그리면 별 그리기 명령은 총 12번 실행돼요.
- **조건문 안의 조건문** — 생명이 남아 있는 경우에만 폭탄에 닿았는지 검사해요.

![엔트리와 스크래치에서 조건문 안에 조건문을 넣은 예](assets/nested-condition.webp "교과서 120쪽")
![숫자를 추측하고 더 큰지 작은지 확인하는 업다운 게임 화면](assets/up-down.webp "교과서 123쪽")

## 함수와 디버깅

**함수**는 특정 일을 수행하는 명령을 묶어 이름을 붙인 것이에요. 엔트리에서 ‘사각형 그리기’ 함수를 한 번 **정의**해 두면 필요한 곳에서 여러 번 **호출**할 수 있어요. 함수 내용을 고치면 그 함수를 부르는 곳에도 변경이 적용돼요.

**매개 변수**는 함수를 호출할 때 전달한 값을 받아 함수 안에서 쓰는 이름이에요. ‘사각형 그리기’ 함수에 변의 길이를 전달하면 같은 명령으로 크기가 다른 사각형을 그릴 수 있어요.

![오각형을 그리는 코드를 함수로 묶기 전과 후](assets/function-compare.webp "교과서 128쪽")

### 오류를 찾고 다시 확인하기

**디버깅**은 실행 결과를 보고 오류가 난 원인을 찾아 수정하는 일이에요. 경고가 나며 실행이 멈추는 경우도 있고, 실행은 되지만 결과가 틀리는 경우도 있어요.

1. 어떤 입력에서 어떤 결과가 나와야 하는지 정해요.
2. 실행해 보고 실제 결과를 기록해요.
3. 예상과 달라진 단계의 조건이나 값을 확인하고 수정해요.
4. 같은 입력과 다른 입력으로 다시 실행해 확인해요.

> 정답이 60인데 43을 입력했을 때 DOWN이 나온다면, ‘입력값 < 정답’일 때 UP을 표시하도록 연결했는지 확인해요. 60과 72도 입력해 정답·DOWN 분기가 제대로 작동하는지 확인해요.

![오류를 발견하고 수정한 뒤 프로그램을 다시 확인하는 장면](assets/debugging.webp "교과서 132쪽")
